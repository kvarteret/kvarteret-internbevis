# ADR-0002: Recurrent Events Display Strategy

**Status:** Accepted  
**Date:** 2026-05-09 (updated 2026-05-10)  
**Deciders:** Martin Kleiven (E-Tjenesten)

---

## Context

### Data model (Sanity)

Each `arrangement` document has:

- **`dates[]`** — an array of `arrangementDate` objects (`startDate: "YYYY-MM-DD"`, `startTime`, `endTime`). Editors add each occurrence manually via the Sanity Studio form.
- **`isRecurring`** — boolean toggle indicating a repeating series.
- **`rrule`** — an iCal RRULE string (e.g. `FREQ=WEEKLY;BYDAY=TU`) stored as plain text, generated by a `RecurrenceBuilder` UI component in the event submission form.

### Fetching (GROQ)

```groq
*[_type == "arrangement"
  && approvalStatus == "approved"
  && (
    count(dates[startDate >= $today]) > 0
    || (isRecurring == true && defined(rrule) && count(dates) > 0)
  )
] | order(
    coalesce(dates[startDate >= $today][0].startDate, dates[0].startDate) asc,
    coalesce(dates[startDate >= $today][0].startTime, dates[0].startTime, "00:00") asc
) {
  ...
  isRecurring,
  rrule,
  "dates": dates | order(startDate asc) { ... }
}
```

Key points:

- Approved events appear if they have **at least one future explicit date**, OR if they are **recurring with an rrule** (even if all explicit dates are in the past).
- For recurring events whose explicit `dates[]` are all past, `dates[0]` (the anchor) is returned as the seed for client-side rrule expansion.
- `$today` is passed as a query parameter at fetch time (Oslo-local `YYYY-MM-DD`).

### Recurring dates — two approaches in parallel

**1. Manual dates array (primary)**  
If an editor added multiple dates manually (e.g. every Tuesday for 3 months), they all appear in `dates[]` and are returned directly from the query.

**2. Rrule expansion (client-side fallback)**  
If the event has only one date in `dates[]` (the anchor) but carries an `rrule`, future occurrences are expanded at render time using the `rrule` npm package:

```typescript
export const expandRruleUpcomingDates = (
    anchorDateStr: string,
    anchorTime: string | null,
    rruleStr: string,
    maxCount = 14,
): Date[] => {
    const rule = new RRule({
        ...RRule.parseString(rruleStr),
        dtstart: new Date(`${anchorDateStr}T12:00:00Z`),
    })
    const now = new Date()
    const ceiling = new Date(now.getFullYear() + 2, now.getMonth(), now.getDate())
    return rule
        .between(now, ceiling, true)
        .slice(0, maxCount)
        .map(d => toOsloDate(d.toISOString().split("T")[0]!, anchorTime))
}
```

`between(now, ceiling)` returns only future occurrences regardless of how old the anchor date is, so the `maxCount` budget is never wasted on past dates.

Up to 3 date chips are shown plus an overflow count (`+N`, capped at `9+`).

---

## Decision

Each `arrangement` renders as a **single card** representing the nearest upcoming date. For recurring events, the anchor date in `dates[0]` may be in the past — it serves only as the `dtstart` seed for rrule expansion, not as the displayed date.

### Source of upcoming date chips

| Condition | Upcoming dates source |
|---|---|
| `dates.length > 1` | `dates[1…]` from Sanity |
| `isRecurring && rrule && dates.length === 1` | Client-side rrule expansion from `dates[0]` as anchor |

### Date chip display

Let `N` = number of upcoming dates after the representative.

| N | Chips shown |
|---|---|
| 0 | *(none)* |
| 1 | `"5. mai"` |
| 2 | `"5. mai"`, `"12. mai"` |
| 3 | `"5. mai"`, `"12. mai"`, `+1` |
| 4+ | `"5. mai"`, `"12. mai"`, `+N` (capped at `9+`) |

---

## Consequences

### Positive

- The feed is not dominated by a single recurring series.
- Users see at a glance that an event is recurring and can plan ahead.
- Rrule expansion via the `rrule` package is robust and consistent with the web (samfunnetibergen) implementation.
- Recurring events remain visible even after their explicit anchor date passes — no manual Sanity maintenance needed to keep them alive.

### Negative / trade-offs

- Rrule expansion happens at render time; there is no server-side guarantee that the generated dates are accurate.
- Linking to a specific future occurrence is not possible from the list view.

---

## Alternatives considered

**Server-side rrule materialisation** — expand rrule into concrete `dates[]` entries via a Sanity webhook or scheduled job. Eliminates the gap entirely. Not implemented due to complexity; deferred.

**Include rrule events unconditionally in the GROQ query** — implemented. The query now includes `isRecurring == true && defined(rrule) && count(dates) > 0` as an OR condition alongside the explicit future-date check.

**Show all occurrences as separate cards** — rejected: recurring events dominate the feed.
